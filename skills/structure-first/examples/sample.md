# 構造先行の例

## 主張

入力: 「API エラーは DB のカラムが不正に消えたのが原因。直した。伝えたい」

構造（先に出す）:

```text
1. 目的: 障害の原因と復旧を共有する
2. 主張: 原因は DB カラムの不正削除で、修正済み
3. 手段・根拠: バックエンド API でエラー → 該当カラムを復元／修正
4. 相手にしてほしいこと: （未定ならここで聞く）
```

ここで「この構造で本文を書いてよいですか？」と聞き、OK が出てから本文へ。

本文（承認のあと）:

```text
共有です。バックエンド API のエラーは、DB 上のカラムが不正に消えていたことが原因でした。修正済みです。
（相手アクションが分かっていればここに書く）
```

## 依頼

入力: 「レビューお願いしたい。認証まわりの PR」

構造:

```text
1. 目的: マージ前に認証変更の妥当性を確認してもらう
2. 依頼内容: PR のレビュー
3. 背景・制約: 認証まわり / 期限は未定
4. 次アクション: Approve または指摘
```

## 悪い構造 → 直す

悪い例（手段が先）:

```text
1. 調査したら N+1 だった
2. プールが枯渇する
3. だから直した
```

良い例:

```text
1. 結論: 昨日の変更で一部画面が遅い。修正済み（または対応中）
2. 影響: 一部ユーザーの表示遅延
3. 原因: DB アクセス増（詳細は後段）
4. 相手アクション: 対応不要 / 確認だけ など
```
