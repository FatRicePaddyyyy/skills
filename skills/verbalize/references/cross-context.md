# 自明な前提は相手には無い

部署・職種をまたぐ会話で一番重要なのは、「自分にとって自明な前提は、相手には存在しない」ことを前提に会話を設計すること。

Yahoo! JAPAN のエンジニア向け記事でも、部署・職種をまたぐコミュニケーションでは「目的・単語・成果物」を確認し、共通認識を作ることを勧めている。本スキルの枠（目的・成果物）と、下の「同じ言葉でも同じ意味とは限らない」がそれに当たる。

## 話す前に考える5つ

1. **相手は何を知っている？**
   「このプロジェクトの経緯を知ってる」「この略語は通じる」などを勝手に仮定しない。特に部署固有の常識・略語・過去の経緯は危険。
2. **相手は何を求めている？**
   「技術を理解したい」のか、「納期を判断したい」のか、「Yes/Noを決めたい」のかで必要な情報が全然違う。相手の意思決定に不要な情報は削る。ゴールから逆算して情報量を絞る。
3. **結論→理由→必要なら詳細、の順にする。**
   エンジニアはつい「調査したらAで、内部ではBになっていて、それでCが……なので3日必要です」と説明しがち。他部署にはまず「3日必要です」→「理由は○○です」でいい。相手が必要なら技術詳細に降りる。
4. **技術用語ではなく、相手への影響に翻訳する。**
   「DBのコネクションプールが枯渇する」ではなく、営業相手なら「アクセスが増えるとユーザーが操作できなくなる可能性があります」。技術用語そのものより、その結果何が起こるのかを伝える。
5. **同じ言葉でも同じ意味とは限らない。**
   「リリース」「完成」「対応済み」「今週中」あたりは部署によって意味がズレやすい。「完成＝本番公開まで？」のように、重要な言葉だけ認識を合わせる。

## 流れ（単純化）

相手のコンテキストを推測する
→ 相手が今回判断したいことを特定する
→ その判断に必要な情報だけ選ぶ
→ 相手の言葉に翻訳する
→ 結論から伝える

これは「相手が何を求めているか考えて、情報を削る」能力そのもの。

特に最後の **「相手に何をしてほしい／何をしなくていいのか」** まで伝える。

## 例: 障害を営業に話す

弱い例:

```text
昨日デプロイしたAPIでN+1が発生していて、DB負荷が……
```

強い例:

```text
昨日の変更に問題があり、一部ユーザーで画面表示が遅くなっています。今日中に修正予定です。営業側での対応は不要です。技術的にはDBアクセスが増えているのが原因です。
```
