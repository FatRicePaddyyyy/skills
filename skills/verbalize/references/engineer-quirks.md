# エンジニアの伝え方のクセ

出典: IDH「[エンジニアのコミュニケーション課題とは？](https://idh-net.co.jp/recruit/blog/conversation-problems/)」（2025-08-22）。

話が通じないのは性格や努力不足ではない。正確・論理的な思考が、そのまま言葉に出ているだけ。調整するのは順序と前提の置き方。

## よくあるクセ

聞き手には「何が言いたいの」になる。本人には自然。

| クセ | 起きること | 直し |
| --- | --- | --- |
| 主語が無い | 「やる必要があります」→ 誰が何を、が不明 | 誰が / 何を を書く |
| 抽象・専門から入る | 「ここの非同期処理が非効率で…」→ 何の話か不明 | 結論と対象を先に。用語は一言補足 |
| 説明の順序が逆 | A→B→C の工程から入る → 何が問題か見えない | 結論 → 必要なら背景 |
| 工程・背景を全部話す | 論理的なつもりが長い | 枠の外は削る |
| 冷静な分析 | 「皮肉」「冷たい」と読まれる | 困りを一文認めてから事実 |
| 途中で解決案 | 「最後まで聞いてくれない」 | 聞き終わる。抽象なら具体化の質問を先に |
| 事実だけ | 「無関心」「非協力」と読まれる | 関心の対象は事実。相手の状況は無視しない |

リモートでは空気と表情が落ちるので、このクセは増幅する。

## 非エンジニアとのギャップ

前提が違うすれ違い。一方の努力だけでは完結しないが、エンジニア側でできること:

- **抽象的な要望**（「もっとユーザーフレンドリーに」）→ 咀嚼して具体の質問を返す。「ボタン配置、文字サイズ、どれが気になりますか」
- **無理な依頼**（「明日までいける？」）→ 「できない」で切らず、制約と代替を添えて相談する。「設計と検証で 2–3 日。急ぎなら A だけ先」
- **モヤっとした言い方**（「なんか使いにくい」）→ 丁寧に問い直す。「どの部分でそう感じましたか」

## 現場チェック

- 話し始めは結論。背景はあと
- 専門用語は一言補足。「これって通じるかな」を先に見る
- 途中で「ここまで大丈夫そうですか」
- 複雑なら図か箇条書き。話す前に紙（または枠）で整理
- 「ダメです」ではなく「こうすると良くなる」
- 主語を省略しない。「なぜその話をしているのか」を意識する
