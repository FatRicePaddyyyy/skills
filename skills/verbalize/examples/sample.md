# 言語化の例

## フェーズ1（状況の整理）

入力: 「ログイン、なんか遅い気がする」

出力:

```markdown
- 感覚: 待たされている。以前より引っかかる
- 状況: ステージングのログイン画面。メール＋パスワード。今日の午後に気づいた
- いま気になる点: 送信してからダッシュボードが出るまでの間が、記憶より長い
```

まだ原因も報告文も書かない。

## フェーズ2（気づきの深化）

入力: 上のメモ

出力:

```markdown
- 事実: ログイン API は 200 を返している。画面遷移まで約 4s。先週の録画では約 1s
- 仮説: プロフィール取得が直列で、かつタイムアウト寸前まで待っている（根拠: 遷移完了が API 成功より遅い）
- まだ見ていないこと: プロフィール API のレイテンシ、フロントの await 順、直近の依存更新
```

「遅い」を性能全般に広げない。事実と仮説を混ぜない。

## フェーズ3の前（情報が足りない）

入力: 「ログイン遅い件、チームに書いて」

出力: 本文を書かず、足りない項目だけ聞く。分かっていることは聞かない。

```markdown
メッセージを書くために、次だけください。不明なら「未定」で構いません。
- 相手のペルソナ（役割・いま知っていること・今回判断したいこと・チャネル）
- 目的 / やること / やらないこと／スコープ / 期限 / 成果物
- 相手に何をしてほしい／何をしなくていいのか
- 事実（いつから、誰に、どのくらい遅いか。分かっている範囲で）
```

## フェーズ3（他者への伝達）

入力:

```markdown
ペルソナ: 同じチームのバックエンド。ログイン API は知っている。フロントの画面遷移は見ていない。関心は原因と修正範囲。チャネルは Slack。
目的: 遅さの切り分け結果を共有し、修正方針の合意を取る
やること: 原因の共有、修正案の提示、レビュー依頼
やらないこと／スコープ: 今回はプロフィール API の高速化はしない。画面の文言変更もしない
期限: 明日のスタンドアップまで方針決定
成果物: Slack 投稿 1 本と、合意後の Issue
```

調査済み。プロフィール API が直列 await されていた。

弱い例（調べた順）:

```markdown
まず Network を見て、ログインは速かったです。
次にフロントを読んで、await が直列なのに気づきました。
直近の PR でプロフィール取得が増えていました。
直したほうがいいと思います。
```

強い例（枠 → ペルソナ向けの本文）:

```markdown
- **目的:** 遅さの切り分け結果を共有し、修正方針の合意を取る
- **やること:** 原因の共有、修正案の提示、レビュー依頼
- **やらないこと／スコープ:** プロフィール API の高速化はしない。画面文言も変えない
- **期限:** 明日のスタンドアップまで方針決定
- **成果物:** この投稿と、合意後の Issue

ログイン後の画面表示が約 4s。ログイン API 自体は約 200ms なので、認証は壊れていない。
遅いのは認証成功後、プロフィール取得を直列 await しているため。影響は全ユーザーの初回遷移。
再現: ステージングでログアウト→ログインし、ダッシュボード表示までを測る。
対処案: プロフィール取得を画面表示のクリティカルパスから外す / 並列化する。明日までにこの方針でよいかだけ欲しい。
```

結論 → 影響 → 条件 → 詳細。体験の再生ではない。
事実（客観カメラ）と対処案（主観カメラ）を混ぜていない。接続は「なので」「ため」で論理が飛んでいない。

## ハサミ（推敲）

弱い例:

```markdown
今回の件については、いろいろ調べてみたところ、ログインに関して遅さを感じる部分がありまして、
もったいないので調査ログも残しつつ共有できればと思いまして…
```

強い例: 上の「強い例」本文。調査ログは削る。「〜しまして」を言い切る。図にするなら `ログイン成功 → プロフィール await（直列） → 画面表示 4s`。

## 伝わらなかったとき

相手: 「で、ログイン壊れてるの？」

ギャップ: 「遅い」が障害なのか性能なのか、結論が先に無かった。
組み直し: 先頭を「壊れてはいない。認証は成功する。遅いのはその後の画面表示」にする。

## 伝え方のクセ

弱い例（主語なし・専門から・工程から）:

```markdown
やる必要があります。ここの非同期処理が非効率で、A→B→C の順で動いていて…
```

強い例:

```markdown
画面表示が遅いので、プロフィール取得の待ちを外したい（担当: フロント）。
ログインそのものは成功している。遅いのはそのあと、プロフィール API を直列で待っているため。
```

## ふわっとした依頼

入力: 「もっとユーザーフレンドリーにして。明日まで」

出力: 実装案を出さず、具体化と相談。

```markdown
「ユーザーフレンドリー」は、ボタン配置・文字サイズ・手順の少なさのどれが近いですか。
明日までの全改修は設計と確認で足りません。急ぎなら、ログイン後の待ち時間だけ先に直せます。どちらにしますか。
```

## 他部署（営業）へ障害を伝える

弱い例:

```text
昨日デプロイしたAPIでN+1が発生していて、DB負荷が……
```

強い例:

```text
昨日の変更に問題があり、一部ユーザーで画面表示が遅くなっています。今日中に修正予定です。営業側での対応は不要です。技術的にはDBアクセスが増えているのが原因です。
```

影響 → 期限 → してほしい／しなくていい → 必要なら技術。N+1 やデプロイは先に出さない。
